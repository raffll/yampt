## Step 0 — Kiro Config (steering, docs, hooks, skill)

Hooks (`clang-format-on-create.json`, `clang-format-on-save.json`) are valid and
consistent. The audit skill frontmatter, categories, paths, and `known-issues.md`
reference are all accurate. The following internal-consistency problems were found
in the steering and docs set.

### Finding 1

**Category:** Steering contradictions
**Location:** `.kiro/steering/code-style.md` — "GUI Log Tab Headers" section (last section)
**Problem:** The rule documents the operation-name API as `log_tab_t::append_log(operation_name, text)`. No class `log_tab_t` exists anymore; the class was renamed to `log_view_t` (in `yampt.translator/source/view/log_view.hpp`), and the method is `log_view_t::append_log`. The rule's own "View Class Suffix" section even lists `log_tab_t` as a BAD name to avoid, so the file simultaneously forbids the name and uses it as the canonical reference. Stale class reference in a steering rule.
**Evidence:** code-style.md: "The `log_tab_t::append_log(operation_name, text)` first argument…"; and in the same file, the bad-example list: "class log_tab_t : public QWidget". Actual header: `class log_view_t : public QWidget { … void append_log(const std::string & operation_name, const std::string & log_text); … }`.
**Proposed fix:** Rename the reference in the "GUI Log Tab Headers" section from `log_tab_t::append_log` to `log_view_t::append_log` (and consider retitling the section "GUI Log View Headers" for consistency).

### Finding 2

**Category:** Steering contradictions
**Location:** `.kiro/steering/code-style.md` — "No Duplicated Utility Functions" and "Path Handling" sections
**Problem:** The rule states shared string/path helpers must live in `yampt/utility/string_utils.hpp`. The real path is `yampt.core/source/utility/string_utils.hpp`. There is no `yampt/utility/` directory. A steering rule points developers at a path that does not exist.
**Evidence:** code-style.md: "Common string/path operations must live in one shared location (`yampt/utility/string_utils.hpp`)." Actual file: `c:\OMEN\Morrowind\yampt\yampt.core\source\utility\string_utils.hpp`.
**Proposed fix:** Correct the path to `yampt.core/source/utility/string_utils.hpp` in both the "No Duplicated Utility Functions" header line and anywhere else the short `yampt/utility/...` form appears.

### Finding 3

**Category:** Steering contradictions
**Location:** `.kiro/docs/design-decisions.md` (two references) and `.kiro/docs/translation-engine-build.md` (one reference)
**Problem:** Three docs reference a sibling doc `project-paths.md` that does not exist in `.kiro/docs/`. The only project-layout doc is `project-structure.md`. These are stale cross-references — a reader following them finds nothing.
**Evidence:** design-decisions.md: "The getpccell `'X'`-marker/back-2-bytes trick is documented in project-paths.md." and "(see MSBuild discovery in `project-paths.md`)". translation-engine-build.md: "(see MSBuild discovery in `project-paths.md`)." File search for `project-paths` returns no file.
**Proposed fix:** Repoint all three references to `project-structure.md` (which contains the MSBuild `vswhere` discovery block) or to wherever the getpccell `'X'`-marker note now lives, and remove the dangling `project-paths.md` name.

### Finding 4

**Category:** Steering contradictions (rule-vs-reference drift / stale reference)
**Location:** `.kiro/docs/project-structure.md` — "Repository Layout" tree vs. "Project Dependency Graph" section
**Problem:** The Repository Layout ASCII tree lists `yampt.core`, `yampt.cli`, `yampt.translator`, `yampt.editor`, `yampt.tests` — but omits the `yampt.qt/` project entirely, even though `yampt.qt` is a real project (`yampt.qt/yampt.qt.vcxproj`) and the same document's "Project Dependency Graph" and "Dependency Rules" sections describe it as a core StaticLibrary that editor/translator/tests link. The top-of-file layout contradicts the bottom-of-file graph within one doc.
**Evidence:** The layout tree jumps from `yampt.core/` straight to `yampt.cli/` with no `yampt.qt/` entry; later the same file states "yampt.qt (StaticLibrary → yampt.qt.lib)". Disk shows `c:\OMEN\Morrowind\yampt\yampt.qt\source\` with 7 classes.
**Proposed fix:** Add a `yampt.qt/` node to the Repository Layout tree (with its `source/` contents and `yampt.qt.vcxproj`) so the layout matches the dependency graph and the solution.

### Finding 5

**Category:** Knowledge-base drift
**Location:** `.kiro/docs/project-structure.md` — Repository Layout, `yampt.core/source/decoder/` and `utility/` bullets
**Problem:** The decoder-folder description is stale. It lists `decoder/` as containing "conflict_slots, sub_record_iter, sub_record_schema, view_tree_format, content_alignment, view_group_def", but the actual folder also contains `field_encoder`, `field_validator`, `record_header_flags`, and `scvr_condition`. **Evidence:** `Get-ChildItem decoder` shows field_encoder/field_validator/record_header_flags/scvr_condition in addition to the listed files; `record_behavior.hpp/.cpp` resolve under `yampt.core\source\utility\`.
**Proposed fix:** Update the decoder bullet to include the four missing files and add `record_behavior` to the utility bullet (or generalize the lists and lean on the "vcxproj.filters are authoritative" note, which the file already states).

### Finding 6

**Category:** Knowledge-base drift
**Location:** `.kiro/docs/project-structure.md` — "yampt.qt — Qt Bridge Library" → "Current contents"
**Problem:** The listed current contents of yampt.qt are `theme_system`, `conflict_types`, `settings_store`, `path_resolver`. **Proposed fix:** Add `resource_paths` and `translation_example` to the "Current contents" list for yampt.qt.

## Step 2 — Code Audit

### Finding 7

**Category:** Architecture violation / Steering drift (one class per file)
**Location:** `yampt.core/source/scanner/sub_record_merge.hpp` + `sub_record_merge.cpp`
**Problem:** Two distinct public behavior classes — `sub_record_merge_t` and `leveled_list_merge_t` — share a single `.hpp/.cpp` pair. code-style.md ("File Organization" / "Code Quality") is explicit: "One class per file" and "One class = one `.hpp` + one `.cpp`. Never split a class across multiple `.cpp` files." The converse (two classes in one file) is the same violation. Both classes have external callers (`leveled_list_merge_t::merge` is called from `patch_builder.cpp`, `auto_merge.cpp`, and tests), so `leveled_list_merge_t` is a first-class unit that warrants its own file. code-style.md itself cites `leveled_list_merge_t::merge()` as an example of a dedicated testable class, implying a dedicated file.
**Evidence:** `sub_record_merge.hpp` declares both `class sub_record_merge_t` and `class leveled_list_merge_t`; `sub_record_merge.cpp` defines `leveled_list_merge_t::merge` at line ~1784. Callers: `patch_builder.cpp:103`, `auto_merge.cpp:187`.
**Proposed fix:** Extract `leveled_list_merge_t` into its own `scanner/leveled_list_merge.hpp/.cpp` pair, update includes in the three call sites and the test, and add the new `.cpp` to `yampt.core.vcxproj` + `.filters`. This is additive/mechanical and does not alter merge behavior.

### Finding 8

**Category:** Steering drift (max 1000 lines per file)
**Location:** `yampt.core/source/scanner/sub_record_merge.cpp` — 1818 lines
**Problem:** Exceeds the hard 1000-line file limit. Not listed in known-issues.md. It is not one of the sanctioned exceptions (Qt main-window `_setup.cpp`, or a Qt tree model). Extracting `leveled_list_merge_t` (Finding 7) removes part of the bulk; the remaining `sub_record_merge_t` is still likely over 1000 and should be split by responsibility (e.g. CELL/FRMR phase, keyed-list phase, field/bit merge predicates).
**Evidence:** Line count 1818 for `sub_record_merge.cpp`.
**Proposed fix:** After extracting `leveled_list_merge_t`, split the remaining merge logic into cohesive helper classes/files (keeping each below 1000 and preserving behavior, per the No-Regressions rule). Report-only; no change without approval.

### Finding 9

**Category:** Steering drift (max 1000 lines per file)
**Location:** `yampt.core/source/decoder/sub_record_schema.cpp` — 1733 lines
**Problem:** Exceeds the 1000-line limit and is not in known-issues.md. The file is predominantly declarative schema tables (`field_def_t` rows, per-record layouts). The 1000-line rule is stated unconditionally; even granting that table data is lower-risk than logic, this file is the largest non-exception core file and is a candidate for splitting the schema tables by record family (items, dialogue, world/CELL, leveled) into separate translation units.
**Evidence:** Line count 1733 for `sub_record_schema.cpp`.
**Proposed fix:** Either split the schema tables into per-family `.cpp` files that register into the same lookup, or add an explicit acknowledged-exception entry to known-issues.md if the project decides table files are exempt. Report-only.

### Finding 10

**Category:** Steering drift (max 1000 lines per file)
**Location:** `yampt.editor/source/controller/merge_controller.cpp` — 1181 lines
**Problem:** A single controller class (`merge_controller_t`) in a 1181-line file, over the 1000-line limit and not in known-issues.md. `_controller_t` is a sanctioned class suffix but not a sanctioned file-size exception (only Qt main-window `_setup.cpp` and Qt tree models are). The orchestration responsibilities (merged-patch lifecycle, lock save/load, copy operations, session sync) are separable.
**Evidence:** Line count 1181 for `merge_controller.cpp`; header declares a single `class merge_controller_t`.
**Proposed fix:** Extract a cohesive sub-responsibility (e.g. merged-patch lock persistence `save/load_merged_patch_locks`/`sync_active_locks`, or the copy-to-merge operations) into its own controller/helper class with its own file. Report-only.

### Finding 11

**Category:** Steering drift (max 1000 lines per file)
**Location:** `yampt.editor/source/view/plugin_workspace_view.cpp` — 1066 lines
**Problem:** A single `_view_t` Qt widget class in a 1066-line file, over the limit and not in known-issues.md. A plain view widget is not the "Qt tree model with complex decode" exception, and it has no `_setup.cpp` companion sanctioned for it.
**Evidence:** Line count 1066 for `plugin_workspace_view.cpp`; header declares a single `class plugin_workspace_view_t : public QWidget`.
**Proposed fix:** Split out a cohesive piece (e.g. the Lua-scan worker interaction or the plugin-table population) into a helper, or add a companion per the main-window `_setup.cpp` precedent if the project extends that exception to this widget. Report-only.
