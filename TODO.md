# Bugs

editor: flag rows (and NPC/creature attribute rows) have no working copy-to-merged-patch menu item. Flags are bits packed into ONE fixed-width integer field (u8/u16/u32) inside a sub-record (e.g. WPDT Flags = u32 at offset 28, "Magical" = bit 0, "Silver" = bit 1); there is no separate binary region per flag or per the "Flags" presentation group. In the tree, flags render as a group node (label = the flags field name, `type` = the sub-record type e.g. "WPDT", `size` = sub-record size, NO `binary_ranges`) with the bits as child rows (carrying `schema_field_index` + `bit_index`, no `type`). In `show_view_menu`'s kind lambda both the flags-group row and the bit rows classify as `field_of_schema`; the group row has `schema_field_index < 0` so the original `build_source_copy_menu` breaks with no item, and a bit's parent-walk stops at the flags-group node (non-empty type, no binary range) so Copy Field gets `field_bin = -1` and no-ops. A "Copy Sub-Record" attempt (resolve the enclosing real sub-record and offer copying the whole sub-record) was tried and REVERTED — the menu item still did not appear on flags in testing, root cause not yet pinned down (add a diagnostic log at the flags-row menu-build point: which `kind`, whether the enclosing sub-record resolves, and whether the record is already in the merge so build_source_copy_menu vs build_copy_to_merge_menu runs). The correct copyable unit for a flag is the flags FIELD (the whole integer, all bits) or the whole enclosing sub-record — a single bit can't be a byte range. Note: this is the same family as the attribute-copy issue (fields inside a sub-record with no own binary anchor); fixing one should fix both. Also still open: the always-anchorless rows (Record Header / Signature / Record Flags, the `--- INFO Chain ---` separator and its INAM rows, any synthetic `other`-kind row) have no copy path by construction — decide whether any should.
