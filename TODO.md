editor: cannot manually copy NPC/creature attributes (user confirmed: "Charisma, Strength, etc." — i.e. the NPDT attribute fields; Charisma = Personality; didn't say NPC_ or CREA, so check both). Attributes live in NPDT: for NPC_ (NPDT-52) they are individual `field_of_schema` rows (Strength/Intelligence/... u8); for CREA (NPDT-96) they are u32 fields under a `group = "Attributes"`. Both carry a valid `schema_field_index`. KEY FINDING: the "group" is not a separate binary region — attributes are FIELDS inside the single NPDT sub-record (for CREA nested under a presentation group `fdef.group = "Attributes"`; for NPC_ flat under NPDT). `merge_controller_t::copy_group` copies a range of WHOLE sub-records via `group_row.binary_ranges[col]` (built by `compute_group_ranges` only from children that are themselves sub-records, e.g. CELL FRMR object groups / SCVR conditions). The Attributes group's children are fields of ONE sub-record, so it has no valid `binary_ranges` → `copy_group` bails ("no binary range for column"). And Copy Field needs the field path to resolve to that sub-record. So neither Copy Group nor Copy Field cleanly applies to NPDT attribute rows — the actual copyable unit is the whole NPDT sub-record (one binary blob holding level + all attributes + stats). The likely fix is to expose "Copy Sub-Record" (the enclosing NPDT) from attribute/group/field rows, or make field-level copy patch a single field within NPDT. REPRODUCE FIRST on both NPC_ and CREA (which attribute row, which column, is the record already in the merge or not), confirm the exact `row_kind_t`/`binary_ranges`/`schema_field_index` at the click, then fix the copy path for attribute rows. ROOT CAUSE (hypothesis, reproduce first): `element_wise_merge` merges PER BYTE, not per field. `sub_record_merge_t::merge_bytes_three_way` starts from the winner's bytes and, for each byte where `inter != first && winner == first`, takes the intermediate's byte. For a multi-byte numeric field (WPDT u16/u32 stats — damage/weight/value/reach), if the intermediate mod changed one byte of the field and the winner changed a different byte of the same field, the merge splices a low byte from one side and a high byte from the other into a number neither mod set — typically landing between the two values. WEAP/WPDT, ARMO/AODT, NPC_/CREA NPDT/AIDT/AI_W all use `element_wise_merge` (record_behavior.cpp), so all are affected; rare because it needs two mods editing different bytes of the same multi-byte field.
